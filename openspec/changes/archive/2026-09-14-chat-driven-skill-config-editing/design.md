# Design: chat-driven-skill-config-editing

## Context

现状：需求变更唯一入口是人手动编辑 SKILL.md「采集需求」节 → 兜底轮检测 skillHash → 群确认 →「开始」激活 → 派生 config/计划任务。@FF 交互会话只认 开始/暂停/状态 三个逐字指令，自由文本一律回绝（wecom-bot-control-commands spec）。本变更在该会话上加「对话起草」能力，动机见 proposal.md。

约束：@FF 会话 cwd 是 `~/.openclaw/workspace`，操作项目文件一律用绝对路径；台账/状态文件沿用原子写 + 写前重读约定；企微群消息会截断长文本，指令必须极简；群内仅李非凡 + FF 两成员。

## Goals / Non-Goals

**Goals:**
- 自然语言变更请求 → 精确草案（改前/改后对照）→「写入」落盘 → 写后校验/回滚
- 三类对象分级生效：需求块（再要「开始」）、重要性规则（写入即生效）、白名单 config（写入即生效+验证）
- 全生命周期留痕，可审计"谁、何时、原话、改了什么"

**Non-Goals:**
- 不做身份鉴权（群内两人前提，成员变化时重新评估）
- 不做多草案排队（同时只一个待写入草案，新的顶掉旧的；草案不设时间过期，与「需求无过期」一致）
- 重要性规则不做整节自由重写，只条目级增删改
- 白名单外的 config（openclaw 全局配置、密钥）一律不碰
- 不改 Python 脚本、不改计划任务、不新增依赖

## Decisions

**D1：对话路径是"代笔前端"，不另开生效通道。**
草案「写入」后只是把变更写进 SKILL.md/config 文件，需求块仍走既有 hash 检测→确认→「开始」激活。生效闸门数量不变，config 唯一来源（台账派生）不变。
备选：对话直接改 config——否决，破坏台账唯一事实来源，绕开确认闸。

**D2：先草案后落盘（两阶段），而非收到请求立即改文件。**
用户拍板。代价是每次变更多一轮「写入」往返；收益是落盘前必有人眼核对改前/改后对照，LLM 解析错误被闸门兜住。

**D3：草案独立存 `state/chat-drafts.json`，不进需求台账。**
草案是"可能成为需求的草稿"，台账只记正式需求（固定三个 ID 的生命周期）。草案写入成功后，需求块类变更自然进入台账流程，两者职责不混。
备选：扩展台账加「草案」状态——否决，污染正式需求的状态机与审计语义。

**D4：草案内同时存"改前内容"，回滚直接写回。**
对照回显本来就需要改前内容；同一份数据兼任回滚快照，省去独立备份机制。git 跟踪作为最后兜底，不作为主回滚手段。

**D5：重要性规则条目级编辑。**
草案对规则节的操作限定为「新增条目/删除条目/修改条目」，diff 以条目为单位呈现。禁止整节自由重写——自由文本重写是写乱 skill 文件风险最高的操作。
备选：允许整节重写+完整 diff——否决，diff 过长在企微里难核对，违背"精确性"初衷。

**D6：运维 config 白名单写死在 SKILL.md。**
初始白名单：`config/wecom-aibot.json` 的群名字段、`config/triage-message.txt` 全文。每项附写后验证方式（群名→sessions list 匹配）。白名单本身的增改只能手工改 SKILL.md，不能对话改（防止通道配置被对话连锁改坏后失联）。
备选：白名单也可对话改——否决，失联风险。

**D7：意图分类交给 LLM，落盘动作全部确定性。**
解析可以自由理解，但草案内容一旦确认，落盘是"把草案里的最终形态原样写入"，不做二次自由发挥。写入后立刻按文件类型跑确定性校验（JSON 解析、需求块提取、群名验证）。

**D8：指令集只加「写入」「放弃」，维持逐字匹配。**
与 开始/暂停/状态 同款极简风格，规避企微截断。「写入」无参数、只作用于当前唯一待写入草案（D3/单草案决定的）。

## Risks / Trade-offs

- LLM 解析错误（删错版本、改错字段）→ 确认闸 + 改前/改后对照强制回显；歧义只追问不动笔（spec：歧义澄清）
- 落盘写坏文件（JSON 块损坏、章节结构破坏）→ 写后校验 + 草案内存改前内容直接回滚；git 兜底
- 群名改错导致推送通道中断 → 写后立即 sessions list 验证新群名，失败自动回滚并报告
- @FF 会话与兜底轮并发写 SKILL.md/台账 → 沿用原子写 + 写前重读； SKILL.md 同时被人和 bot 编辑的概率极低，冲突由 git 可追
- 自由文本分类误触发（闲聊被当成变更请求）→ 草案本身零副作用（不落盘），误生成草案由「放弃」或新草案取代消化
- 企微截断长回显 → 回显 diff 控制紧凑，超长按聚合模板同款策略截断并注明

## Migration Plan

纯文档/行为规范变更：改 `skills/intranet-message-triage/SKILL.md`（职责边界、控制指令节、新增对话草案节），`state/chat-drafts.json` 运行时自建。既有 file-first 路径（人改文件→确认）完全保留，无数据迁移。回滚 = revert SKILL.md 并删除 chat-drafts.json。上线后按 tasks.md 演练三类草案各一次。
