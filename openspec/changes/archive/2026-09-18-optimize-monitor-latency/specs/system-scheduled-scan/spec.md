## MODIFIED Requirements

### Requirement: 计划任务注册幂等

系统 MUST 提供注册脚本在 Windows 计划任务中创建或更新「常驻守护任务」：该任务以登录触发方式启动 py 扫描脚本的常驻模式（持续轮询），并配置失败自动重启、周期性看门狗触发器（任务死亡后在看门狗周期内自动重新拉起，运行中因 IgnoreNew 为空操作）与隐藏窗口；重复执行注册 MUST 更新既有任务而不是创建重复任务。任务 MUST 以项目根目录为工作目录调用扫描脚本，常驻轮询间隔取自已激活需求（`scanIntervalSeconds`，缺省 5 秒）。

#### Scenario: 首次注册

- **WHEN** 首次运行注册脚本
- **THEN** Windows 计划任务中存在该常驻守护任务，手动触发一次后扫描进程进入常驻轮询，state 与日志正常落盘，且用户登录会话中不弹出可见控制台窗口

#### Scenario: 重复注册更新而非重复

- **WHEN** 再次运行注册脚本（参数相同或不同）
- **THEN** 既有任务被更新，系统中不出现重复的常驻守护任务，且不会同时运行两个常驻扫描进程

#### Scenario: 崩溃自动重启

- **WHEN** 常驻扫描进程异常退出
- **THEN** Windows 计划任务按配置自动重新拉起常驻扫描，无需人工干预

#### Scenario: runner 死亡后看门狗拉起

- **WHEN** 常驻守护任务的 runner 进程死亡、任务实例结束（无论是否触发失败重启）
- **THEN** 周期性看门狗触发器在下一个周期自动重新启动任务，常驻扫描恢复，无需人工干预

### Requirement: 需求激活驱动调度同步

需求经 @FF 确认激活后，claw MUST 调用注册脚本使常驻守护任务与已激活需求保持一致（含轮询间隔）；处于「待确认」状态的需求 MUST 不影响常驻守护任务。

#### Scenario: 确认后同步频率

- **WHEN** 需求被确认激活且 `scanIntervalSeconds` 与当前常驻轮询间隔不同
- **THEN** 常驻守护任务被重建或常驻进程被重启，使轮询间隔更新为新值

#### Scenario: 未确认不动调度

- **WHEN** 需求处于「待确认」状态
- **THEN** 常驻守护任务与运行中的常驻进程保持原有配置不变

### Requirement: 单调度器铁律

同一时刻 MUST 只有一个调度源驱动 py 扫描。从每分钟 tick 的计划任务迁移到常驻守护任务时，MUST 先注册并验证新任务，验证通过后再删除旧的每分钟 tick 任务；新任务验证失败 MUST 保留旧调度。

#### Scenario: 正确迁移顺序

- **WHEN** 执行调度迁移
- **THEN** 先注册常驻守护任务并手动触发验证，验证通过后才删除旧的每分钟 tick 计划任务

#### Scenario: 验证失败保留旧调度

- **WHEN** 常驻守护任务手动触发验证失败
- **THEN** 旧的每分钟 tick 计划任务仍然保留，扫描不中断

## ADDED Requirements

### Requirement: 常驻单实例保护

常驻扫描进程 MUST 保证同一时刻至多一个实例在运行；第二个实例启动时 MUST 检测到既有实例并立即退出，不产生错误日志噪音。

#### Scenario: 重复启动自动退出

- **WHEN** 已有一个常驻扫描进程在运行，又启动第二个常驻实例
- **THEN** 第二个实例检测到既有实例后安静退出，state 与日志不受干扰

### Requirement: 暂停时安静空转

当已激活需求被暂停、监控目标为空时，常驻扫描进程 MUST 按轮询间隔安静空转（不写错误日志、不触发告警唤醒）；需求恢复激活后 MUST 在下一轮轮询自动恢复采集，无需重启进程。

#### Scenario: 暂停期间无错误噪音

- **WHEN** 全部监控目标需求处于「已暂停」状态
- **THEN** 常驻进程每轮检查 config 后安静跳过采集，`logs/intranet-error/` 不新增记录

#### Scenario: 恢复后自动采集

- **WHEN** 暂停的需求被重新激活且 config 已同步
- **THEN** 常驻进程在下一个轮询周期自动恢复扫描，不需要人工重启进程
